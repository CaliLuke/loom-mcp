# Gemini hosted-code content evaluation

## Decision

Keep provider-hosted code execution unsupported for this release. The pinned SDK
can preserve code/results, but the current framework cannot carry them losslessly
through several independent, closed content boundaries. The measured cost covers
model types and codecs, transcript conversion, child-result presentation, context
accounting, summary/recall policy, and opt-in capture. The investigation establishes
that cost and a workable data representation; it does not establish enough benefit
to justify adopting all those contracts now. No implementation issue is proposed.

Retain the candidate below for a future request with a concrete consumer and an
explicit end-to-end acceptance target. This decision does not enable a provider
tool or change any production code. It completes [#367](https://github.com/CaliLuke/loom-mcp/issues/367)
as an evaluation, separate from continuation and document-input support.

## Problem and evidence

The real pinned `google.golang.org/genai v1.73.0` SDK decodes `ExecutableCode`
(language, code, optional ID) and `CodeExecutionResult` (outcome, output, optional
matching ID). `genai.Tool.CodeExecution` is a request-side enablement surface.
Google documents these response fields as generated by the explicitly configured
hosted tool. Output can be stdout or execution-error text; Python is the documented
language. Sources: [pinned SDK types](https://github.com/googleapis/go-genai/blob/v1.73.0/types.go),
[GenerateContent code/result reference](https://ai.google.dev/api/generate-content#ExecutableCode),
[provider guide](https://ai.google.dev/gemini-api/docs/code-execution).
The guide now primarily demonstrates Interactions; this evaluation exercises the
pinned GenerateContent API and proposes no endpoint or dependency migration.

The [ADK inspiration](https://github.com/google/adk-go/commit/1d2f545) converts child
code/results into a combined text result and trims result trailing newlines. That
presentation choice cannot establish a lossless typed contract here.

Synthetic local HTTP fixtures pass through the actual SDK and the existing
`model.NewClient` boundary. Every request asserts that `tools` is absent. No code
runs, no external provider is called, and this is not a production incident or
proof that an unconfigured provider emits these parts.

| Fixture | Current validated adapter | Candidate typed representation |
| --- | --- | --- |
| `text_only` | One text part succeeds | Same text |
| `code_only` | `response_shape` rejection; usage retained | One executable-code part; never executed locally |
| `result_only` | `response_shape` rejection; usage retained | One execution-result part with exact ID/outcome/output |
| `mixed` | Two text parts succeed; code/result are lost | Text, code, result, text in original order |
| `execution_failed` | Text survives; source and error result are lost | Preserve `OUTCOME_FAILED` and stderr as result data |
| `execution_deadline` | `response_shape` rejection | Preserve `OUTCOME_DEADLINE_EXCEEDED` and partial output as data |
| `unsupported_language` | Text survives; unknown-language code is lost | Reject whole response |
| `unsupported_outcome` | Text survives; unknown-outcome result is lost | Reject whole response |
| `unsupported_metadata` | Text survives; thought-marked signed code is lost | Reject whole response in this bounded candidate |

All fixtures have valid usage of 13 tokens. Successful current responses contain
no host tool calls. Code/result-only output is **not** an empty success. Mixed
loss is an unsupported-capability limitation, not a newly enabled feature.

## Retained proof

- [Raw SDK response fixtures](../../features/model/gemini/testdata/hosted_code)
  retain IDs, exact code/output bytes (including trailing newlines), outcomes and
  array order. Corresponding `.proposed.json` files show the candidate wire shape.
- [Current-boundary evaluation](../../features/model/gemini/hosted_code_evaluation_test.go)
  checks actual SDK decoding, absence of tool enablement, current output or typed
  rejection, and retained usage.
- [Representation evaluation](../../features/model/gemini/hosted_code_proposal_test.go)
  is a test-only mapping, not an adapter or model API. It compares the proposed
  wire fixtures and reconstructs the original supported SDK parts after JSON
  round-trip. It rejects unknown language/outcome/metadata and disabled hosted
  parts. Current model JSON decoding rejects the proposed unimplemented kinds
  before any provider call. This proves representability, not framework support.

Reproduce without credentials or live execution:

```sh
go test -short ./features/model/gemini -run TestHostedCodeEvaluation -count=1
go test -race -short ./features/model/gemini -run TestHostedCodeEvaluation -count=1
```

## Candidate contract, not an adopted capability

The smallest credible future representation consists of two assistant-only parts:

```go
ExecutableCodePart { ID string; Language CodeLanguage; Code string }
CodeExecutionResultPart { ID string; Outcome CodeExecutionOutcome; Output string }
```

Their JSON kinds would be `executable_code` and `code_execution_result`. Accept
Python source with nonempty code and results with `OUTCOME_OK`, `OUTCOME_FAILED`,
or `OUTCOME_DEADLINE_EXCEEDED`; empty output is valid. Preserve IDs and all string
bytes without trimming or newline insertion. IDs remain inert provider metadata,
not host tool IDs or authorization references. Standalone code/result parts are
valid observations; do not fabricate missing partners or invent execution events.
Unknown enums, multiple payload fields, and code/result reasoning metadata reject
before output is published. Existing ordinary thinking remains separately typed.

Host configuration would explicitly opt in at Gemini/Vertex adapter construction,
with runtime factory forwarding. Default off must reject any hosted code/result
output, including mixed responses; merely receiving those parts must not enable
execution. A positive setting permits adding `genai.ToolCodeExecution` to the
provider request. No model-authored data can toggle it. Other providers and
unconfigured Gemini clients reject these typed history parts before I/O.

The future first subset would be unary GenerateContent with no simultaneous host
tool definitions or structured-output request. Those combinations would reject
before I/O until independently supported. Stream remains unsupported. No model
allowlist or SDK upgrade follows from this evaluation; unsupported provider/model
combinations retain ordinary provider errors. Execution failure outcomes remain
content, with no automatic retry, tool dispatch, or synthetic run failure. Normal
transport failures and `MAX_TOKENS` retain their existing rejection semantics.

Strings and part counts consume the existing canonical output/request budgets
(16 MiB owned-byte limit, collection/depth limits), including IDs and enum text.
Validated messages, retained usage and content remain one canonical invocation;
provider-side execution is not a host model-call reservation or host tool call.
No new execution service, sandbox, network fetch, artifact store, workflow, or
implicit tool-result attachment capability is part of this candidate.

Canonical replay must preserve exact accepted data without re-executing code.
Adding model types alone does not prove workflow replay compatibility. Any actual
change to workflow-executed logic must bump the workflow protocol and include
recorded-history replay proof under repository rules. This evaluation changes no
workflow or production behavior and requires no protocol bump.

## Why defer adoption

SDK availability solves representation at one boundary. The fixtures prove both
faithful SDK decoding and subsequent framework loss. The inventory identifies
multiple additional contracts, especially the nested-agent result schema and
summary/recall projection, which cannot be inferred from raw provider fields.
There is no measured task-quality or caller-outcome evidence in this investigation
to outweigh that compatibility work. Retaining unsupported behavior and these
fixtures is therefore the bounded release decision.

A future adoption request should identify the consumer that needs typed source
and execution outcomes, choose its child-result schema, and demonstrate benefit
with local acceptance scenarios before proposing implementation. That separate
work must include failing end-to-end tests, docs/skill updates, provider
conformance and repository gates; protocol/replay work applies only when workflow
behavior changes. No new implementation issue or external publication is part of
this evaluation.
