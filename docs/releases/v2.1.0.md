Loom-MCP 2.1 adds context management for long-running agents, durable run records
and evaluation tools, a Selvedge execution backend, and new model capabilities.
These are the major changes since **v2.0.1**. This release also changes generated
APIs and workflow contracts; read the upgrade guidance before replacing workers.

## Long-running agents

Agents can compact older context, summarize evicted material, and retrieve the
original evidence through `recall_context`. Context settings can be declared in
the DSL or overridden for a run. Successful runs can carry compacted context
into the next run in the same session. Image and document recall is available
when the selected providers support those attachments. Threshold compaction
requires explicit configuration or an application-qualified default; no
production model qualifications ship enabled.

The runtime now stores transcript content and tool results by reference rather
than repeatedly carrying the full history through workflow activities. A
per-run model-call limit bounds planner, summary, retry, and finalizer calls.
Context-window overflow has its own error classification and bounded recovery.

## Agent testing and evaluation

`agenttest`, `expect`, and `trajectory` provide scripted model responses, typed
tool stubs, and assertions over actual agent runs. `RunRecord` reconstructs model
requests, tool results, child runs, and adopted or abandoned attempts from durable
stores. Records can be exported for offline inspection; sharing uses an explicit
application disclosure policy.

The new evaluation runner and embeddable CLI run scenarios across variants,
retain experiments on disk, compare results, and apply calibrated model judges
or strict checks to stored verdicts. Candidate editing, retained-evidence
inspection, controlled submissions, and explicit component reuse support
iterative agent development. See the
[agent testing guide](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/agent_testing.md).

## Durable execution with Selvedge

Selvedge joins Temporal and the in-memory engine as an execution backend, using
SQLite or PostgreSQL. It supports durable activity retry and timeout policies,
worker replacement, and portable history export and replay. Separate worker and
client modes let applications submit work without running a worker in every
process. Backend capabilities differ; see the
[engine guide](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/runtime.md#available-engines).

## Model and embedding support

A new Codex provider supports subscription credentials and native reasoning
effort. OpenAI Responses accepts inline PDF input; Gemini supports bounded
continuation with usage accounting; Ollama supports reasoning-effort settings.
Anthropic and supported Bedrock Claude models can receive images and documents
in tool results. Streaming and replay preserve completed message boundaries,
provider-issued reasoning, and disjoint cache-token accounting.

The new [embedding client](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/embeddings.md)
supports single-text and batch requests to Ollama, validates returned vectors,
and rejects silent input truncation. Applications retain ownership of chunking,
indexing, and storage.

## MCP and runtime correctness

The official MCP Go SDK is now the sole wire transport. Generated servers use a
shared runtime bridge, while generated service bindings retain their typed
contracts. Callers gain elicitation callbacks, stdio frame limits, and an
identifiable HTTP user agent. Projected tools support server-injected fields and
bounded structured results.

Argument validation now follows the advertised schemas before service dispatch,
including empty payloads and untagged object unions. Resource query decoding
preserves declared scalar and array types. Other fixes cover response content
negotiation, session-principal binding, origin checks, safe error messages,
tool-await ordering, cancellation, and stale registry admissions.

## Upgrade

Use **Go 1.27.4 or later** and **Loom v1.10.0**. Provider SDKs, Temporal, SQLite
support libraries, and database test baselines have also been refreshed; the
[dependency guide](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/dependencies.md)
records the versions and migrations.

```sh
go install github.com/CaliLuke/loom/cmd/loom@v1.10.0
go get github.com/CaliLuke/loom@v1.10.0 github.com/CaliLuke/loom-mcp/v2@{{version}}
loom gen <module-import-path>/design
```

**Drain running workflows before deploying new workers.** This release uses
workflow protocol 21 and rejects older or unstamped histories. There is no
in-place migration of running executions. Workers and replayers must use the
matching protocol.

Regenerate services and transports together. Applications using the removed
native MCP transport must switch to `NewSDKServer`, remove obsolete MCP-only
JSON-RPC packages and DSL declarations, and use standard progress notifications
and resource updates. Follow the
[MCP migration steps](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/mcp_sdk_server.md#migration-from-native-mcp-transport).

Custom planners, engines, stores, and hook consumers must adopt the current
view/content-loader and typed activity contracts. Tool results and oversized
startup-hook inputs can be references; resolve their content through the run
store. Production workers and clients must share persistent stores when records
need to survive process replacement. Review the
[runtime guide](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/runtime.md)
for these API changes.

Custom model adapters must use typed `Chunk` variants and provide a terminal
`Response()` after literal `io.EOF`. Wrap providers with `model.NewClient`;
clients return `ValidatedStreamer`, and consumers must call `Finalize` with
their terminal result. Follow the
[model client contract](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/overview.md#model-client-interface).

For MongoDB run logs, stop old-version writers before upgrading and let startup
migration finish before resuming writes. The adapter adds sequence positions to
legacy records; mixing old and new writers is unsupported. See the
[run-log migration guidance](https://github.com/CaliLuke/loom-mcp/blob/{{version}}/docs/runtime.md#run-event-store-runlogstore).

Existing Pulse deployments require a coordinated migration to membership
version 2. Stop older participants before migrating; restarting alone is
insufficient, and old and new binaries must not share affected streams. Follow
the [Pulse migration guidance](https://github.com/CaliLuke/loom/blob/v1.10.0/docs/pulse.md).
